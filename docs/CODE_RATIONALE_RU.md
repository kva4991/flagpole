# Подробное обоснование кода: ESP32-C3 и Android

Этот документ специально подготовлен как развёрнутое объяснение, почему код в проекте написан именно так.

> Документ объясняет намерение handoff, но не подтверждает реализацию. Найденные
> расхождения приведены в [`AUDIT_V061_RU.md`](AUDIT_V061_RU.md). §status1

## Часть 1. ESP32-C3

### Почему выбрана ESP32-C3

1. Дешёвая и доступная плата.
2. Есть BLE.
3. Есть аппаратный PWM.
4. Есть режим Deep Sleep.
5. Для проекта не нужен Wi‑Fi как обязательная функция.

### Почему выбрана библиотека NimBLE-Arduino

Стандартный BLE-стек ESP32 исторически более тяжёлый по памяти. NimBLE-Arduino компактнее и лучше подходит для простого периферийного устройства с кастомным сервисом.

### Почему сервис один, а характеристик несколько

Использован один кастомный BLE-сервис с несколькими характеристиками:

- `status` — чтение и уведомления;
- `control` — запись команд;
- `config` — чтение конфигурации.

Это проще, чем распылять логику на множество сервисов.

### Почему команды строковые

Для первого рабочего прототипа строковый протокол — самый понятный:

- читается глазами;
- легко тестируется;
- не требует жёсткой сериализации;
- проще объяснить следующему чату.

### Почему BLE-окно ровно 1 час

Это прямое решение по требованиям пользователя. Оно балансирует удобство первичной настройки и энергосбережение.

### Почему не сделана постоянная память о «доверенном режиме BLE» между перезагрузками

Пользователь прямо указал, что это не нужно и бессмысленно. Поэтому код не записывает такой флаг во flash.

### Почему смена PIN реализована как команда в защищённой сессии

Устройство не имеет кнопок и экрана. Поэтому менять PIN логично через приложение уже после успешной авторизации. Проверка старого PIN исключает случайную или несанкционированную смену.

### Почему после смены PIN удаляются bond-записи

Это требование проекта: старая авторизация должна перестать работать. Иначе смена PIN была бы неполной.

### Почему BLE-выключение сделано отдельной командой

Это безопаснее, чем пытаться автоматически гасить BLE сразу после первой сессии. Пользователь сам решает, когда завершить обслуживание устройства.

### Почему PWM идёт прямо на MOSFET

Это минимальная и надёжная схема. Внешний PWM-контроллер здесь избыточен: у нас один канал, и ESP32-C3 с этим отлично справляется.

### Почему частота PWM умеренная

Проект ориентирован на реальный уличный прототип, а не на лабораторный идеал. Слишком высокие частоты могут добавить ненужные вопросы по конкретному MOSFET-модулю, а умеренная частота работает предсказуемо.

### Почему VEML7700 калибруется вручную

Потому что реальные условия установки заранее неизвестны. Световой тоннель, высота, отражения и положение мачты всё равно потребуют полевой подстройки.

### Почему Deep Sleep не используется ночью при активной подсветке

При активном PWM и активном BLE это бессмысленно и вредно. Ночью главный потребитель — подсветка, а не ESP.

## Часть 2. Android

### Почему приложение локальное, без интернета

Устройство физически рядом. Интернет здесь только усложнил бы архитектуру, снизил надёжность и увеличил бы объём разработки.

### Почему поиск устройства идёт по имени `Crucian`

Это упрощает интерфейс: пользователь не видит список из десятков BLE-устройств, а приложение целится в одно конкретное устройство проекта.

### Почему выбран Compose

Экран небольшой, динамический и состоит из стандартных элементов управления. Compose позволяет держать весь UI в коде, а не размазывать логику по XML.

### Почему приложение умеет менять PIN

Это ключевая административная функция устройства. Поскольку у навершия нет физического интерфейса, такая возможность обязательно должна существовать в приложении.

### Почему добавлена команда `BLE:OFF`

Это позволяет завершить режим обслуживания без отключения питания снизу. Полезно после настройки и калибровки.

### Почему приложение показывает текущее состояние, а не только кнопки

Пользователь должен видеть, что происходит: текущий lux, температура, батарея, режим, яркость. Без этого управление стало бы слепым.
