# Почему код ESP32-C3 и Android написан именно так

## 1. Общий принцип

Устройство находится на улице, питается от аккумуляторной системы и должно продолжать работать без телефона. Поэтому архитектура разделена:

- ESP32-C3 самостоятельно управляет светом и датчиками;
- Android — только локальный сервисный интерфейс;
- отсутствие приложения или BLE не должно выключать автоматику;
- ошибки датчика света должны переводить нагрузку в безопасное состояние.

# Часть I. ESP32-C3

## 2. Единое имя проекта

Прошивка не содержит строку `Crucian` непосредственно в рабочем коде. Она читает generated-константу:

```cpp
cfg::DEVICE_NAME
```

Её источник — `project_identity.json`. Это позволяет другому владельцу изменить имя BLE, не правя C++ вручную.

## 3. Почему NimBLE

NimBLE используется для BLE-сервера с bonding, PIN и кастомными GATT-характеристиками. Проекту не нужен облачный протокол: локальный BLE уменьшает количество внешних зависимостей.

## 4. Почему часовой период хранится через RTC

После Deep-sleep ESP32-C3 снова выполняет `setup()`. Обычный `millis()` начал бы час заново. Поэтому блокировка BLE после завершения окна хранится в RTC-памяти и сбрасывается только при настоящем включении питания.

Это реализует требование:

```text
power-on → BLE 1 час → нет bonding → BLE до следующего power cycle выключено
```

Если bonding прошёл успешно, BLE остаётся активным до снятия питания или команды `BLE:OFF`.

## 5. Почему PIN не читается через GATT

PIN нужен только процедуре pairing. Возвращать действующий PIN уже авторизованному клиенту бессмысленно. Конфигурация сообщает только, используется ли заводской PIN.

## 6. Почему смена PIN удаляет bonds

Без удаления bonding ранее доверенный телефон мог бы продолжать подключаться по старым ключам. После команды смены PIN прошивка:

1. проверяет старый PIN;
2. сохраняет новый;
3. удаляет все bond-записи;
4. разрывает соединение.

## 7. Почему протокол текстовый

Команды:

```text
MODE:AUTO
BRIGHTNESS:75
CALIBRATE:DAY
PIN:123456,654321
```

удобно читать в Serial и универсальном BLE-клиенте. Это важнее нескольких сэкономленных байтов для редких сервисных команд.

## 8. Почему PWM и MOSFET одновременно

ESP не питает 12-вольтовую ленту. MOSFET коммутирует силовой ток, а аппаратный PWM ESP управляет затвором. Это две части одной схемы.

Частота 500 Гц выбрана как умеренная для первой проверки конкретной платы LR7843. После стенда её можно скорректировать.

## 9. Почему нет внешнего PWM-контроллера

Канал один. Аппаратный LEDC ESP32-C3 уже формирует PWM. Внешний контроллер увеличил бы размеры, потребление, соединения и количество отказов без достаточной пользы.

## 10. Почему VEML7700 имеет fail-safe

VEML7700 непосредственно определяет необходимость подсветки. При трёх последовательных ошибках нагрузка выключается независимо от AUTO/ON/OFF. До достижения лимита яркость не пересчитывается по недостоверному значению.

## 11. Почему калибровка выполняется на установленном устройстве

Световой тоннель ограничивает угол зрения. Его реальное пропускание зависит от окна, печати, загрязнения и окружения. Поэтому телефон задаёт текущий свет как «день» или «ночь», а прошивка сохраняет проверенную пару порогов.

## 12. Почему AHT20+BMP280 не управляет светом

Климатический модуль является диагностическим. Его отказ не должен выключать флаг. Только отказ VEML7700 влияет на световой fail-safe.

## 13. Почему напряжение аккумулятора не измеряется

Владелец решил не реализовывать эту функцию. В прошивке и Android нет фиктивного поля батареи. Внешняя система 6×18650 должна отдельно обеспечивать стабилизированные 12 В.

# Часть II. Android

## 14. Почему приложение ищет устройство по generated-имени

Приложение использует `ProjectIdentity.BLE_DEVICE_NAME`, сгенерированное из того же JSON, что и прошивка. После смены имени обе стороны остаются синхронизированы.

## 15. Почему нужна BLE state machine

BLE-подключение состоит из последовательных фаз:

1. разрешения;
2. сканирование;
3. подключение;
4. MTU;
5. bonding;
6. поиск сервисов;
7. подписка;
8. чтение конфигурации;
9. готовность.

Явный `BlePhase` не позволяет интерфейсу считать соединение готовым раньше времени и даёт понятные сообщения об ошибке.

## 16. Почему GATT-операции стоят в очереди

Android BLE ненадёжно выполняет параллельные descriptor/read/write операции. Поэтому клиент хранит одну активную операцию, ожидает соответствующий callback и только затем запускает следующую.

Начальная очередь:

```text
CCCD write → config read → STATUS? write
```

## 17. Почему есть тайм-ауты

Callback может не прийти из-за телефона, стека или потери связи. Без тайм-аута UI навсегда завис бы на одном этапе. Есть отдельные лимиты сканирования, подключения и GATT-операций.

## 18. Почему используются современные и старые Android API

На Android 13+ используются методы записи с массивом данных в аргументе. Для Android 8–12 оставлен ограниченный fallback с deprecated API, потому что `minSdk=26`.

## 19. Почему BluetoothGatt обязательно закрывается

`disconnect()` не освобождает все системные ресурсы. При завершении клиента выполняются:

- остановка сканирования;
- очистка очереди;
- disconnect;
- close;
- отмена coroutine scope;
- снятие BroadcastReceiver.

## 20. Почему callback передаются на main thread

Compose-состояние должно обновляться предсказуемо. BLE callbacks могут приходить не на UI-потоке, поэтому изменения проходят через `Handler(Looper.getMainLooper())`.

## 21. Почему интерфейс пока одностраничный

У устройства один локальный сценарий: подключить, проверить, откалибровать и настроить. Дополнительная навигация не приносит пользы первому прототипу.

## 22. Граница готовности

Код реализует требуемую архитектуру, но реальная готовность подтверждается только тестами:

- несколько моделей Android-телефонов;
- неверный и правильный PIN;
- смена PIN и повторное pairing;
- потеря связи на каждом этапе;
- повторное сканирование;
- очередь команд;
- команда `BLE:OFF`.
