# ADR-0016: Android BLE state machine и последовательная GATT-очередь

- Статус: Принято
- Дата: 2026-08-01

## Контекст

Android BLE выполняет GATT-операции асинхронно и на разных версиях системы использует разные API записи. Параллельные операции и незакрытые соединения приводили бы к гонкам и утечкам.

## Рассмотренные варианты

1. Вызывать чтения и записи непосредственно из UI без очереди.
2. Добавить только задержки между командами.
3. Реализовать явную state machine, одну активную операцию, очередь и тайм-ауты.

## Решение

Android-клиент использует:

- явные состояния сканирования, подключения, MTU, bonding, поиска сервисов, подписки, чтения конфигурации и готовности;
- только одну активную GATT-операцию;
- очередь descriptor/read/write;
- тайм-ауты;
- современные API записи Android 13+ с совместимым fallback;
- остановку сканирования, disconnect и `BluetoothGatt.close()` при завершении клиента;
- передачу callback-результатов на main thread.

## Последствия

Параллельные GATT-команды и незакрытые соединения приводят к нестабильности на разных телефонах. Для уличного устройства нужен предсказуемый порядок операций.

Клиент стал объёмнее, зато состояние подключения видно в UI, операции сериализованы, а завершение жизненного цикла освобождает GATT.

## Проверка

Собрать APK, проверить очередь и тайм-ауты автоматическими тестами, затем испытать сканирование, bonding, уведомления, команды и повторное подключение на реальном телефоне и ESP32-C3.

## Когда пересматривать

При изменении BLE-протокола, минимальной версии Android, появлении нескольких одновременных устройств либо подтверждённых зависаниях на конкретных телефонах.
