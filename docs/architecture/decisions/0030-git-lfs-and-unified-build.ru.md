# ADR-0030: Git LFS и единый сборочный интерфейс

- Статус: Принято
- Дата: 2026-08-03

## Контекст

STL и GLB занимают основную часть рабочего дерева и меняются как цельные бинарные файлы. Одновременно ручная регенерация требовала помнить порядок нескольких Python- и npm-команд. Без ограничения LFS-загрузок каждый CI job мог бы повторно скачивать сотни мегабайт и расходовать месячный трафик владельца.

## Рассмотренные варианты

- оставить все бинарные файлы в обычном Git — отклонено из-за роста будущей истории;
- перенести в LFS также все PNG — отклонено: PNG занимают заметно меньше места и нужны документации и каталогу;
- переписать всю опубликованную историю — отложено как рискованная необратимая операция;
- хранить в LFS все STL/GLB текущего и будущих коммитов, оставить PNG в Git и загружать LFS только в условной механической задаче — принято.

## Решение

`.gitattributes` направляет `*.stl` и `*.glb` в Git LFS. PNG остаются обычными Git-объектами. Миграция применяется новым коммитом без переписывания прежних опубликованных коммитов.

Единым интерфейсом регенерации является `scripts/build.mjs`; Windows запускает его через `build.cmd` или `tools/windows/build.ps1` только из защищённой копии под `FLAGPOLE_EXECUTION_ROOT`. Режимы: `all`, `generate`, `validate`, `catalog`, `ci`.

CI сначала выполняет проверки без загрузки LFS и классифицирует изменённые пути. Только условная задача механики выполняет один `git lfs pull --include="*.glb,*.stl"`. Android и обе прошивки работают с LFS-указателями и не скачивают модели. Проверка SHA-256 и генератор каталога читают исходный hash/size непосредственно из LFS-указателя.

Повторный экспорт STEP/STL/GLB через OCP и рендер PNG не обязаны быть побайтово одинаковыми между Windows и Linux: служебные поля, порядок записи и растеризация могут отличаться при той же геометрии. Производный JSON-отчёт содержит SHA этих GLB, а HTML-каталог — размеры производных превью, поэтому они также проверяются семантически, а не побайтово. Механический CI проверяет все 40 STL на замкнутость, ориентацию и единственный связный объём, выполняет семантические тесты модели и требует побайтового совпадения только от действительно детерминированных identity-файлов и индекса медиа-описаний. `CHECKSUMS_SHA256.txt` проверяет опубликованные артефакты до регенерации, но не используется как критерий межплатформенного совпадения повторно экспортированных CAD-бинарников.

## Последствия

- будущие версии больших моделей не раздувают обычную Git-историю;
- документационные изменения не запускают механическую сборку и не расходуют LFS-трафик;
- один полный механический CI-запуск всё равно скачивает весь набор STL/GLB;
- при текущем объёме это около 427 МБ на механический workflow; документационный, Android- и firmware-only diff расходует 0 МБ LFS;
- новый push той же ветки отменяет незавершённый предыдущий workflow через `concurrency`;
- старые бинарные blobs остаются в прежней истории до отдельного согласованного решения;
- межплатформенная воспроизводимость CAD означает совпадение геометрии, семантики и детерминированных исходных текстов, а не обязательный одинаковый SHA производного бинарника, превью или отчёта с таким SHA;
- для полноценной работы с моделями разработчику требуется Git LFS;
- ZIP GitHub может содержать только LFS-указатели, если включение LFS-объектов в архивы не настроено отдельно.

## Проверка

- `node --test tests/buildSystem.test.mjs tests/windowsToolchain.test.mjs`;
- `build.cmd validate` из защищённой рабочей копии;
- `git lfs ls-files` после индексирования миграционного коммита;
- GitHub Actions должен показать один LFS-download только в механической задаче.

## Когда пересматривать

- при приближении к месячному лимиту LFS-трафика или хранилища;
- при переносе генерируемых моделей в Release assets или внешнее хранилище;
- перед любым переписыванием опубликованной Git-истории;
- если PNG начинают занимать сопоставимый объём или отдельные изображения превышают практический порог Git.
