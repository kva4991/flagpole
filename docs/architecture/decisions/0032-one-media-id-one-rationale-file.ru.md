# ADR-0032: один медиа-ID — один подробный rationale-файл

- Статус: Принято
- Дата: 2026-08-04

## Контекст

`catalog/drawings.json` раньше содержал короткое поле `description`, а часть причин геометрии и представления была распределена между тематическими документами, генераторами и сгенерированным HTML. Следующий агент мог увидеть картинку, но не понять, почему выбран конкретный разрез, ракурс, порядок деталей, открытая дорожка, положение мембраны или уровень упрощения непечатных тел. При переносе текста в несколько мест возникал риск расхождения формулировок.

Владельцу требуется подробное объяснение каждого рисунка, интерактивной 3D-модели и карточки печатной очереди, однозначно связанное с тем же ID и обязательное к чтению/обновлению при моделировании.

## Рассмотренные варианты

- расширить `description` внутри JSON до нескольких страниц текста — отклонено: JSON становится трудно просматривать, править и рецензировать, а Markdown-ссылки и структура разделов теряются;
- хранить один общий большой документ по всем изображениям — отклонено: связь с конкретным ID слабая, конфликтующие изменения труднее заметить, файл быстро превращается в неструктурированный журнал;
- оставить пояснения только в тематических документах — отклонено: один профильный документ относится к нескольким видам и не объясняет выбор камеры, набора объектов и presentation-логики конкретной карточки;
- создать отдельный Markdown-файл для каждого медиа-ID и сделать его единственным подробным текстовым источником — принято.

## Решение

Для каждой записи в массивах `drawings`, `models` и `printSessions` файла `catalog/drawings.json` существует ровно один файл:

```text
catalog/media-descriptions/<ID>.md
```

Имя файла, `id` в его метаданных и ID карточки совпадают. Числовой ID хранится без `#`, а в пользовательском интерфейсе отображается с ровно одним `#`.

`catalog/drawings.json` хранит путь `descriptionFile` и не содержит поля `description`. Краткий текст карточки берётся из `summary` одноимённого Markdown-файла. Сгенерированный `catalog/catalog.html` не является источником текста и вручную не редактируется.

Каждый файл содержит обязательные разделы: назначение, источники, состав вида, причины представления, разбор ID, сборочную/сервисную логику, неподтверждённые допущения, синхронное обновление и проверку. Контракт и формат описаны в `catalog/media-descriptions/README_RU.md`. §mediarationale1

Профильные документы в `mechanical/docs/`, `electronics/` и `docs/` сохраняются. Они описывают общие требования узла и не считаются дубликатом rationale конкретной карточки. Полный повтор одного и того же описания в JSON, README или ручном HTML запрещён; вместо него используется ссылка.

## Последствия

- агент перед изменением рисунка или модели обязан прочитать одноимённый `<ID>.md` и связанные профильные документы;
- изменение геометрии, ракурса, состава сцены, координат выносок, печатной ориентации или статуса требует обновить `<ID>.md` в том же изменении;
- новый медиа-ID нельзя добавить без отдельного файла описания;
- удалённая карточка не оставляет файл-сироту;
- JSON становится структурным источником, Markdown — текстовым источником, HTML — производным представлением;
- карточки печатных очередей могут использовать тот же постер, что раскладки, но имеют собственный ID и отдельный операционный rationale;
- объём документации увеличивается, зато причины решений становятся проверяемыми и локализованными.

## Проверка

- `npm.cmd run media:descriptions:check`;
- `npm.cmd run catalog:generate` и `npm.cmd run catalog:check`;
- `node --test tests/mediaDescriptions.test.mjs tests/catalog.test.mjs`;
- валидатор проверяет соответствие один-к-одному, имя файла, метаданные, существование медиа/источника, обязательные разделы, минимальный объём, отсутствие JSON-поля `description`, отсутствие файлов-сирот и повторов rationale вне ID-папки;
- ручная проверка подтверждает, что summary и ссылка карточки относятся к тому же ID.

## Когда пересматривать

- если каталог перейдёт на другой формат, способный хранить подробный Markdown без дублирования;
- если один медиаобъект получит несколько независимых вариантов с отдельными ID;
- при введении локализованных описаний на нескольких языках;
- если автоматическая сборка документации будет переносить эти файлы в отдельный сайт, сохраняя один источник истины.
