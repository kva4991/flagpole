# ADR-0033: компактный критический контракт в каждом медиа-описании

- Статус: Принято
- Дата: 2026-08-04

## Контекст

Подробные rationale-файлы 29 медиа-ID сохраняют причины геометрии и представления, но их большой объём затрудняет быстрое выделение мелких элементов, которые агент не должен потерять при очередной генерации. Полный текст нужен для понимания причин, однако перед моделированием требуется короткий операционный контракт.

## Рассмотренные варианты

- сократить подробные файлы до нескольких пунктов — отклонено: исчезают причины решений, допущения и сервисная логика;
- хранить один общий чек-лист на все модели — отклонено: он не отражает особенности конкретной карточки;
- добавить в начало каждого ID-файла отдельный краткий контракт и проверять его структуру автоматически — принято.

## Решение

Сразу после строки статуса каждый `catalog/media-descriptions/<ID>.md` содержит раздел `## 0. Критический контракт` с тремя подразделами:

1. `Критические элементы — нельзя потерять`;
2. `Запрещено`;
3. `Проверить после генерации`.

Каждый подраздел содержит минимум два конкретных пункта, относящихся к данному ID. Агент сначала читает этот контракт, затем весь подробный rationale. При изменении модели или чертежа оба слоя обновляются вместе. §mediacontract1

## Последствия

- мелкие закладные, вводы, мембраны, прокладки, маршруты проводов и сервисные доступы видны до чтения длинного текста;
- подробное обоснование не сокращается и остаётся единственным источником причин;
- валидатор не допускает отсутствие или пустой формальный контракт;
- добавление нового медиа-ID требует сразу сформулировать его критические элементы, запреты и проверки.

## Проверка

- `npm.cmd run media:descriptions:check`;
- `node --test tests/mediaDescriptions.test.mjs`;
- валидатор проверяет порядок раздела, три обязательных заголовка и минимум два пункта в каждом;
- ручная проверка подтверждает конкретность пунктов и соответствие изображению.

## Когда пересматривать

- если критический контракт станет машинно извлекаемой частью другого единственного источника без дублирования;
- если появится отдельный интерфейс проверки feature-ID и сервисных признаков CAD;
- если практика покажет, что минимального числа пунктов недостаточно.
